# pmp - partial-tier parametric pipeline on Modal

For every model of the partial tier (`s3://bim-proprietary-data/cad-disk-extract/dataset/packages/3d_partial/<pid>/`):
faithful source IFC -> the headless deterministic build123d pipeline (build scripts, schedules, verification) -> the
colour-coded issue model, generated by the shipped `build_issues_model.py` -> one bundle per model -> merged by the
publisher into the package's own `scripts/` folder. Nothing outside `scripts/` is ever written.

**Scope today: the 5 NEW test models only** (`new5.json`: n1 DB1, n2 DB1 add-on, n3 IFC approximated, n4 IFC
complete-to-source, n5 SDS/2). The original 5 samples are refused by every entrypoint (`app/forbidden_ids.json`), and
any model not in `new5.json` is refused unless `--scale` is passed, which needs the owner's approval first.

```
   PUT URLs (~5-6 h)  ───────────────► │            package IFC: fetched inside the pipeline stage            ~5-6 h URLs)
                                       │ 2 pipeline pipeline_<cls>  job.py's 9 steps, verdict = pmx_summary
                                       │ 3 issues   issues_<cls>    make_issues -> scripts/ tree -> RUN the
                                       │            shipped build_issues_model.py (+ its e2e checks) -> bundle
                                       │ 4 upload   upload_bundle   PUT -> _state/pmp/bundles/<run>/<id>.tar.gz
                                       └ index row /vol/index/<run>/<id>.json -> /vol/index/<run>.jsonl
 publish/box.py publish ──SSM────────────────────────────────────────────────────────────────────────────► publisher.py: verify, merge
                                                                                                             into 3d_partial/<pid>/scripts/
```

No AWS credentials and no Modal secrets on Modal: inputs arrive through pre-signed GET URLs inside the job rows, bundles
leave through pre-signed PUT URLs. URLs are bearer tokens: they are never printed, logged, or written to the volume or
the index (only `bucket/key` and the expiry are).

## Size classes and resources (`app/pmpstages/common.py` `RES`)

Class by delivered STEP bytes (decimal). `J` = worker processes given to the tools (as the fleet), `cpu` = Modal
physical cores (2 threads each), step timeout = job.py's per-step table, function timeout = Modal limit for the stage.

| class | STEP bytes | J | cpu | memory (request) | ephemeral disk | step timeout | stage timeout |
|---|---|---|---|---|---|---|---|
| S | < 10 MB | 4 | 2 | 8 GiB | Modal default | 1 h | 4 h |
| M | < 100 MB | 8 | 4 | 24 GiB | Modal default | 2 h | 8 h |
| L | < 500 MB | 16 | 8 | 48 GiB | 512 GiB | 4 h | 16 h |
| XL | < 1 GB | 32 | 16 | 128 GiB | 512 GiB | 8 h | 24 h |
| too_big_v1 | >= 1 GB | - | - | - | - | - | recorded `too_big_v1`, not run |

* A stage stops starting steps 15 min before its timeout; a step not started is recorded rc 124 (as a job.py timeout),
  so the summary and outputs are always written.
* A step killed by the OOM killer (rc -9 / 137) makes the orchestrator re-run the pipeline once more at the next class
  (`--escalate`, default on); every attempt is in the index row (`stages.pipeline_attempts`).
* A stage call that raises (container crash, platform error) is retried twice with back-off; a Modal timeout is not
  retried (it would repeat). Errors are recorded in `stages.<stage>.infra_errors`.
* Preemption: Modal restarts a preempted container with the same input (the stage starts over; inputs and outputs are
  idempotent). Every container start is recorded in `/<id>/logs/starts.jsonl` under the call's token, each stage result
  carries `container_starts`, and the index row `container_restarts` counts the restarts (their compute is lost and
  not in `cpu_seconds`). `PMP_NONPREEMPTIBLE=L,XL` puts those classes on Modal's non-preemptible capacity (billed at 3x list
  price per Modal's preemption guide) - a decision for the scale plan. Measured: the n4 unit test (S) was preempted twice
  in 21 min (3 starts; 1280 s wall vs 832 s for the completed start).
* Safety caps: each stage function `max_containers` = `PMP_STAGE_MAX_CONTAINERS` (default 5); the driver runs
  `--concurrency` models at once (default 4), capped so orchestrators + stage containers stay <= `--max-containers`
  (default 10).

## 4. End to end on the 5 new models

```bash
RUN=new5-$(date +%Y%m%d-%H%M)
python3 publish/box.py presign --run $RUN --ids-file jobs/new5.jsonl          # -> publish/presigned/$RUN.json (0600)
PMP_WITH_PLUGINS=1 .venv/bin/modal run app/modal_app.py::main \
    --jobs jobs/urls/new5.signed.jsonl --run $RUN --put-urls publish/presigned/$RUN.json \
    [--only n4_ifc_c2s,n1_db1_small] [--limit N] [--concurrency 4] [--max-containers 10] [--no-upload] [--dry-run]
```

* `PMP_WITH_PLUGINS=1` builds the `src_db1` / `src_sds2` images from `src_db1/modal_image.py` / `src_sds2/modal_image.py`
  (without it, DB1 / SDS/2 models end `source_failed` with `plugin_image_missing`, IFC models run normally).
* `--dry-run` prints the plan (class, model folder, PUT URL present, runnable) and runs nothing.
* Per model: source -> pipeline -> issues (+ scripts tree + shipped-script runs + bundle) -> upload. The driver prints one
  line per model as it finishes, then merges the index and writes a local copy to `app/runs/<run>.jsonl`.
* PUT URLs live ~5-6 h (the box's role credentials). If they expired before a bundle was ready the model ends
  `upload_failed`; re-upload the bundles already on the volume with fresh URLs:

```bash
python3 publish/box.py presign --run $RUN --ids-file jobs/new5.jsonl
.venv/bin/modal run app/modal_app.py::upload --run $RUN --put-urls publish/presigned/$RUN.json [--only ID,ID]
```

### Index row (`/vol/index/<run>.jsonl`, one per model)

`model_id, tag, pid, model_folder, step, source_kind, bytes, cls, cls_final, code, status, error, stages{source,
pipeline, pipeline_attempts, issues}, bundle{path, bytes, sha256, md5}, upload{object, ok, http, etag, ...}, seconds,
cpu_seconds, peak_gib, container_restarts, started, finished, run`.

`status`: `done` (bundle uploaded) | `bundled` (no PUT URL / `--no-upload`) | `upload_failed` | `issues_failed` |
`pipeline_failed` | `source_failed` | `too_big_v1` | `not_runnable:<why>` | `error`. Nothing is skipped silently.

A pipeline verdict of `perfect=False` is NOT a failure: the model is processed and published with its reasons (the parts
concerned are PURPLE in the issue model). `pipeline_failed` means the stage could not run at all (download / code check).

### Volume layout (`pmp-out`)

```
/<model_id>/source/            provenance.json (+ regenerated / emitted IFC, skipped_records.json, sds2_facts.json)
/<model_id>/pipeline/out/      job.py's flat out folder (schedules, verification, step logs, pmx_summary.json)
/<model_id>/pipeline/summary.json, e2e_inputs.json
/<model_id>/scripts_tree/      the scripts/ tree exactly as bundled (inspection)
/<model_id>/bundle/<run>/      <model_id>.tar.gz, scripts_manifest_rows.jsonl, bundle_facts.json, upload.json
/<model_id>/logs/              starts.jsonl, issues/ (issues.log, issues_runs.log, issues_e2e.json, maker_out/), src_*.log
/index/<run>/<model_id>.json, /index/<run>.jsonl
```

Collect: `.venv/bin/modal run app/modal_app.py::collect --run $RUN` (re-merges the index), or
`.venv/bin/modal volume get pmp-out /<model_id>/scripts_tree ./somewhere`.

### What the issues stage guarantees before a bundle exists

1. the issue maker wrote `schedules/issues.json`, `schedules/missing_parts.json`, `issues/WHERE_TO_LOOK.md`;
2. the tree is assembled per the layout; the shipped `build_model.py`, `steelbuild.py` and schedules are byte for byte
   what the pipeline's e2e step ran (`shipped_build_inputs_equal_e2e_tested`);
3. `python build_issues_model.py` run from `scripts/<model_folder>/` of a package-shaped root (delivered STEP at its
   package path) writes the published `issues/*.step` files;
4. checks (`verification/issues_e2e.json`): rc 0; highlighted STEP written; MISSING-only STEP written iff
   `missing_parts.json` lists parts; a second run (other `--jobs`) gives byte-identical DATA sections;
   `--from-delivered ../../model/step/...` runs clean and leaves the delivered STEP unchanged; `--list` counts equal the
   maker's counts; every reference STEP the maker wrote itself (`ref/`) is reproduced byte for byte;
5. the bundle passes `bundle_lib.verify_bundle` (layout, rows, sha256s).
Any failure -> `issues_failed`, no bundle: a package never receives files its own scripts cannot regenerate.

`clean_venv_check` (`modal run app/modal_app.py::clean_venv_check --model-id ID`, after a run) installs the shipped
`scripts/requirements.txt` into a clean venv and runs `build_model.py --list`, `build_issues_model.py --help/--list`
there, to back the claim that the scripts run from the package alone.

```bash
python3 publish/box.py deploy
```

The publisher (on the box) verifies each bundle against the sha256 in the index, merges it into
`3d_partial/<pid>/scripts/` (shared files must be byte-identical, a model folder belongs to one model id, nothing is
deleted, nothing outside `scripts/` is written), regenerates `scripts/scripts_manifest.jsonl` and logs to
`_state/pmp/publish/<run>.jsonl`. See `publish/README.md`.

## 6. Scale (only after the owner approves)

1. `AWS_PROFILE=bim .venv/bin/python jobs/make_jobs.py` -> `jobs/jobs_partial.jsonl.gz` (all 26,733 rows; `too_big_v1`
   and blocking problems are kept and recorded, never dropped).
2. Batches sized so a batch finishes inside the PUT URL lifetime, or run with `--no-upload` and upload afterwards with
   `::upload` and fresh URLs per batch (bundles wait on the volume).
3. `.venv/bin/modal run app/modal_app.py::main --scale --jobs <batch>.jsonl --run <run> --put-urls ... --concurrency N
   --max-containers M` with `PMP_STAGE_MAX_CONTAINERS` raised to match and `PMP_WITH_PLUGINS=1`; consider
   `PMP_NONPREEMPTIBLE=L,XL`. The workspace is shared: agree the container budget first.
4. Publish per run with `--allow-pids` listing that batch's packages (or `--all-pids` once approved).

Cost accounting per model: the index row has `seconds`, `cpu_seconds` (cgroup usage of the completed starts),
`peak_gib` and `container_restarts`; the stage results carry the container's cpu / memory request.
